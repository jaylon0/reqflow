# Debug Strategy

结构化调试策略，吸收自 superpowers systematic-debugging。

> 原始 skill 参考: `_external/systematic-debugging/SKILL.md`

## 铁律

```
没有根因调查，不允许提出修复方案。
```

任何阶段跳过都是对调试精神的违背。

## 四阶段调试流程

### Phase 1: 根因调查（Root Cause Investigation）

**在尝试任何修复之前，必须完成：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 错误信息通常包含精确解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误码

2. **稳定复现**
   - 能否可靠触发？
   - 精确复现步骤是什么？
   - 每次都发生吗？
   - 如果不可复现 -> 收集更多数据，不要猜测

3. **检查近期变更**
   - 什么变更可能导致此问题？
   - Git diff、近期提交
   - 新依赖、配置变更
   - 环境差异

4. **多组件系统中的证据收集**

   当系统有多个组件（CI -> build -> signing, API -> service -> database）时：
   ```
   对每个组件边界:
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每层状态

   运行一次收集证据，显示哪里断裂
   然后分析证据定位失败组件
   然后调查该特定组件
   ```

5. **追踪数据流**

   当错误深在调用栈中时：
   - 坏值从哪里起源？
   - 谁用坏值调用了这个？
   - 继续向上追踪直到找到源头
   - 在源头修复，不在症状处修复

### Phase 2: 模式分析（Pattern Analysis）

**修复前先找模式：**

1. **找工作的例子** - 同一代码库中类似的工作代码
2. **对比参考实现** - 完整阅读，不要略读
3. **识别差异** - 工作的和坏的之间有什么不同
4. **理解依赖** - 需要什么其他组件、设置、配置

### Phase 3: 假设与测试（Hypothesis and Testing）

**科学方法：**

1. **形成单一假设** - 明确陈述："我认为 X 是根因因为 Y"
2. **最小测试** - 做最小可能的变更来测试假设，一次一个变量
3. **验证后继续** - 成功 -> Phase 4；失败 -> 形成新假设，不要叠加更多修复
4. **不知道时** - 说"我不理解 X"，不要假装知道

### Phase 4: 实施（Implementation）

**修复根因，不修症状：**

1. **创建失败测试用例** - 最简单的复现，修复前必须有
2. **实施单一修复** - 一次一个变更，不做"顺便"改进
3. **验证修复** - 测试通过？没有其他测试坏？问题真正解决？
4. **如果修复不起作用**
   - 尝试次数 < 3: 返回 Phase 1，用新信息重新分析
   - **尝试次数 >= 3: 停下来质疑架构（见下文）**

5. **3+ 次修复失败：质疑架构**

   表明架构问题的模式：
   - 每次修复揭示新的共享状态/耦合/不同位置的问题
   - 修复需要"大规模重构"
   - 每次修复在别处创建新症状

   **停下来质疑基本面：**
   - 这个模式从根本上健全吗？
   - 我们是否"纯粹靠惯性坚持"？
   - 应该重构架构 vs 继续修症状？
   - **与人类伙伴讨论后再尝试更多修复**

## 与 loop-engine 配合

loop-engine 的 observe->classify->localize->patch->verify->review->decide 流程中，debug_strategy 增强了 classify 和 localize 阶段。

## 分类矩阵

| 错误类型 | 特征 | 常见原因 |
|---------|------|---------|
| 编译错误 | 类型不匹配、缺少导入 | API 变更、版本不兼容 |
| 运行时异常 | NPE、ClassCastException | 空值未检查、类型转换错误 |
| 逻辑错误 | 输出不符预期 | 边界条件、算法错误 |
| 集成错误 | 接口调用失败 | 契约不一致、序列化问题 |

## 红旗信号 -- 立即停下回到 Phase 1

如果你发现自己在想：
- "先快速修一下，以后再调查"
- "试试改 X 看看行不行"
- "一次改多个，跑测试"
- "跳过测试，我手动验证"
- "大概是 X，修一下"
- "我不完全理解但这可能行"
- "参考说 X 但我换个方式"
- "主要问题是：[列修复方案没有调查]"
- 在追踪数据流之前提出解决方案
- **"再试一次"（已经试了 2+ 次）**
- **每次修 revealing 新问题在不同位置**

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题简单，不需要流程" | 简单问题也有根因。流程对简单 bug 也快。 |
| "紧急，没时间走流程" | 系统化调试比猜测乱试更快。 |
| "先试这个，再调查" | 第一个修复定下模式。从头做对。 |
| "修完再写测试" | 未测试的修复不持久。先写测试证明它。 |
| "一次修多个省时间" | 无法隔离哪个有效。导致新 bug。 |
| "参考太长，我适配模式" | 部分理解保证 bug。完整阅读。 |
| "我看到问题了，修吧" | 看到症状 != 理解根因。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **1. 根因** | 读错误、复现、检查变更、收集证据 | 理解 WHAT 和 WHY |
| **2. 模式** | 找工作例子、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小测试 | 确认或新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 解决、测试通过 |

## 何时流程揭示"无根因"

如果系统化调查揭示问题确实是环境相关、时序依赖或外部的：
1. 你已完成流程
2. 记录你调查了什么
3. 实施适当处理（重试、超时、错误信息）
4. 添加监控/日志供未来调查

**但：** 95% 的"无根因"案例是调查不完整。
